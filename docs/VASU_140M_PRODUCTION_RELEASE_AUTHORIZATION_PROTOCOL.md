# VASU-140M Production Release Authorization Protocol

Status: specification only  
Date: 2026-07-30  
Scope: one construction of `vasu_140m_instruction_seed_v1`  
Training authority: none

## Problem

The accepted production builder requires an exact repository commit in its
qualification and authorization inputs. Storing an authorization record inside
the commit it authorizes is impossible: adding the record changes the commit,
which changes the value the record would need to contain.

The protocol must authorize exactly one production publication without:

- circular Git identities;
- treating independent review as authorization;
- allowing later implementation changes;
- allowing reuse after a successful publication;
- authorizing model training;
- creating an authorization record during specification or review.

## Alternatives considered

### Authorization committed before publication

This is rejected. A record cannot bind the hash of the commit that contains
itself. Binding its parent commit instead leaves the runtime commit ambiguous
unless a second identity rule is introduced.

### Authorization committed after publication

This is rejected. Publication would occur before the authoritative approval
record existed, so the builder could not fail closed.

### Detached authorization envelope with two Git identities

This is selected. The reviewed implementation is pinned by an immutable anchor
commit and implementation-file SHA-256. The authorization envelope separately
binds an exact clean runtime commit that must descend from the anchor. The
envelope is stored outside tracked Git state until it is consumed. Its own
canonical SHA-256 provides immutable identity without affecting either commit.

This resolves the circularity while preserving exact runtime provenance.

## Fixed identities

The first protocol version is bound to:

- release ID: `vasu_140m_instruction_seed_v1`;
- reviewed implementation anchor:
  `c014716ec38ef8f08842356fc016359dc5a233d7`;
- implementation path:
  `vasu/data/vasu_140m_production_release.py`;
- implementation SHA-256:
  `0efb0189b4b0c5a8621da9053d56db57d95ebf5b0f1bb59753952ec8afa5d1e2`;
- post-commit qualification SHA-256:
  `ed6f64b9d5cb97925bc68186b4ec403de6e25dc484e33cb103ed05ee977f5cd6`;
- assignment SHA-256:
  `59481237acd2164f96dbbdc2b837ca8cabb00c496b1b6c42cb260b44bbd2b394`.

The runtime commit is intentionally not fixed by this design. It becomes fixed
only in a future authorization envelope after implementation of this protocol
has been accepted and the repository is clean.

## Artifact classes

### Reviewed implementation anchor

The anchor identifies the accepted builder implementation. The runtime commit
must contain the anchor in its ancestry and the implementation file must retain
the exact reviewed SHA-256. An ancestry check alone is insufficient.

### Runtime commit

The runtime commit is the exact `HEAD` used for qualification and publication.
It may be a documentation-only descendant of the implementation anchor. Before
authorization is issued, an independent identity review must prove:

- the runtime commit exists and is the observed `HEAD`;
- the worktree and index are clean;
- the implementation anchor is an ancestor;
- the implementation file SHA-256 is exact;
- qualification reproduces the frozen identities;
- protected production paths and receipt paths are absent.

Once written into an authorization envelope, the runtime commit is immutable.
Publication rejects any other `HEAD`.

### Detached authorization envelope

The authorization envelope is canonical JSON stored at an operator-supplied
path outside the repository worktree. It must not be committed, generated by
the builder, inferred from review, or placed in a protected production path.

Required fields:

```json
{
  "schema_id": "vasu.production-release-authorization.v2",
  "authorization_id": "<unique stable ID>",
  "release_id": "vasu_140m_instruction_seed_v1",
  "authorization_scope": "construct_once",
  "approved_by": "<explicit human approver>",
  "approval_date": "YYYY-MM-DD",
  "expires_date": "YYYY-MM-DD",
  "implementation_anchor_commit": "<40-hex commit>",
  "runtime_commit": "<40-hex commit>",
  "implementation_path": "vasu/data/vasu_140m_production_release.py",
  "implementation_sha256": "<64-hex SHA-256>",
  "qualification_sha256": "<64-hex SHA-256>",
  "assignment_sha256": "<64-hex SHA-256>",
  "external_manifest_template_sha256": "<64-hex SHA-256>",
  "receipt_path": "data/manifests/vasu_140m/authorization_receipts/<authorization_id>.json",
  "publication_path": "data/processed/vasu_140m/instruction_seed_v1",
  "external_manifest_path": "data/manifests/vasu_140m/instruction_seed_v1.json",
  "publication_overwrite_allowed": false,
  "training_authorized": false,
  "authorization_sha256": "<SHA-256 of canonical JSON without this field>"
}
```

The future implementation may add fields, but it must not omit or weaken these
bindings. Dates are UTC calendar dates. Expiration must be bounded by policy
and checked at publication time.

### Consumed receipt

After successful publication, the builder atomically writes the existing
versioned receipt inside the repository. It binds the authorization SHA-256,
runtime commit, implementation SHA-256, qualification SHA-256, and final
external-manifest SHA-256. Receipt presence makes the authorization ID
permanently non-reusable.

The receipt is evidence of consumed construction authority. It is not training
authority.

## Lifecycle

1. Accept this design through independent GPT-5.5 review.
2. Implement schema validation and detached-envelope loading without creating
   an envelope.
3. Freeze qualification fixtures and adversarial tests.
4. Obtain independent implementation acceptance.
5. Commit the accepted implementation and evidence.
6. Select the exact clean runtime commit and reproduce qualification.
7. Obtain a separate runtime-identity review.
8. A human approver may create exactly one detached envelope.
9. Run a non-mutating preflight against that envelope.
10. Only after explicit user instruction, invoke publication once.
11. Validate the published release and consumed receipt.
12. Commit publication evidence separately if repository policy authorizes it.

Steps 8 and 10 are explicit authority boundaries. Earlier steps do not imply
either one.

## Fail-closed validation

Publication must reject:

- an envelope inside the repository worktree;
- missing, extra, malformed, or non-canonical fields;
- an invalid self-hash;
- an unknown schema or scope;
- an absent or non-human approver;
- future approval, expired approval, or excessive validity window;
- a runtime commit unequal to clean `HEAD`;
- an anchor that is not an ancestor of the runtime commit;
- an implementation-file hash mismatch;
- any qualification, assignment, template, path, or release-ID mismatch;
- `training_authorized` other than `false`;
- overwrite permission other than `false`;
- existing production, external-manifest, staging, temporary, or receipt paths;
- reuse of an authorization ID or authorization SHA-256;
- mutation between preflight and publication;
- any incomplete or unverifiable post-publication state.

Unknown fields should be rejected in v2 so approval scope cannot be expanded
silently.

## Crash and concurrency rules

The existing atomic staging and validation design remains authoritative. The
protocol implementation must additionally:

- acquire an exclusive, atomically created publication lock bound to the
  authorization SHA-256;
- reject a pre-existing lock unless a separately reviewed recovery procedure
  proves it stale;
- never delete a receipt, completed release, or external manifest;
- preserve incomplete published directories for quarantine;
- ensure two processes cannot consume the same envelope concurrently.

Lock recovery must be implemented and independently reviewed before real use.

## Review and authorization separation

An independent reviewer may accept design, implementation, or runtime identity.
That reviewer must not be represented as the human publication approver unless
the human explicitly makes that separate decision.

The following phrases never authorize publication:

- `Decision: accept`;
- `tests passed`;
- `qualification reproduced`;
- `ready for authorization`;
- `production_release_review_accepted`.

Only a valid detached envelope plus an explicit instruction to invoke the
publisher can authorize one construction.

## Compatibility

- Checkpoints and optimizer state: unchanged.
- Tokenizer: unchanged and hash-bound.
- Existing datasets and masks: unchanged.
- Planned VASU-140M release bytes: unchanged if construction is later
  authorized.
- Existing v1 test fixtures: retained as historical implementation evidence.
- Training: remains unauthorized.
- Exact resume: unaffected.

## Required implementation evidence

A future implementation review must include tests for:

- canonical schema and self-hash validation;
- rejection of in-repository envelopes;
- clean exact-runtime-commit enforcement;
- anchor ancestry plus exact implementation hash;
- expired, future, overlong, malformed, and scope-expanded envelopes;
- envelope, authorization-ID, receipt, and concurrent reuse;
- publication locking and injected crashes;
- Windows junction, symlink, open-handle, and atomic-create behavior;
- disk exhaustion and mutation after preflight;
- unchanged qualification and release identities;
- explicit proof that no training entry point or authority was added.

## Current decision

This document recommends the detached two-identity protocol for independent
design review. It creates no authorization envelope and authorizes no
publication, dataset construction, checkpoint selection, or training.
